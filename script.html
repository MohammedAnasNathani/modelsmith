ModelSmith: Slide-by-Slide Speaking Script (16 slides)

Speak in first person, pause on bold numbers, point at the diagram while you read it out. Each slide is 30-60 seconds except slide 8 and 14 (demo anchors, 90-120 seconds).

Slide 1 - Title: "Analyze once. Optimize smart. Deploy anywhere."

Say: "Good morning. This is ModelSmith. You upload a trained neural network once, and the platform does four things for you: it measures the model, suggests how to make it smaller for the device you actually deploy on, runs that plan for real, and proves the smaller model still gives the same answers as the original."

Then: "Let me start with the problem."

(Pause 2 seconds, click.)

Slide 2 - The problem and what we built instead

Say: "There are three gaps in the way model compression is done today. One, you cannot see where the size is hiding - which layers hold the parameters. Two, choosing between quantization, pruning or distillation is guesswork done by experts with ad hoc scripts. Three, nothing proves the compressed model still behaves correctly."

Point at the diagram: "The manual loop today is trial, error, hope. What we built instead is one pipeline: upload, analyze, plan, execute, download - with recorded reasons and measured proof."

Slide 3 - Jobs run in the background

Say: "Every operation in ModelSmith is a job row in the database. Compression runs in the background with live progress, so the page never blocks. If a job crashes, the status shows the real error - a failed job retries once, then fails permanently with the truth. Everything is stored: the model, the plan, the artifacts, the metrics. Nothing lies about its state."

Slide 4 - How it is built (architecture)

Say: "We deliberately kept the architecture simple. There is no external queue - a worker thread pool runs inside the FastAPI process, which is right at this scale. The front end is fully detached static JavaScript, so it can be hosted anywhere. And there are two ways to execute: locally on this machine, or remotely on an AWS runner."

Slide 5 - Analysis

Say: "When you upload, we measure: parameter count, FLOPs, forward-pass latency - five warm-up passes, then thirty timed runs. We break down the parameter share layer by layer, which is what lets the planner aim at the right layers. This is why our numbers are defensible: every number in the report comes from a real forward pass."

Slide 6 - Hardware profiles

Say: "The target device is selected first, not last. We have five hardware profiles - the plan is filtered and scored against the device, never dropped in afterwards. Read this table: different devices change what gets ranked. A plan that is great on a workstation can be impossible on an edge device, and the planner knows it before running anything."

Slide 7 - The planner

Say: "The planner keeps a knowledge base of seven techniques and builds eight candidate combinations. Every candidate is scored with this formula: size saved, latency gain, memory saved, accuracy kept - each with explicit weights from the objective you pick. Balanced weights are 0.30, 0.30, 0.20, 0.20. The top plan is recommended, and - this is the important part - rejected plans are kept on screen with a written reason."

Slide 8 - The two headline plans

Say: "On one end, edge-lite: INT8 quantization plus ONNX export - least risk, readable everywhere. On the other, edge-max: INT8 plus pruning at forty percent plus ONNX - the deep cut. In our best measured run, the model went from 93.8 KB to 29.7 KB - a 68.3 percent reduction - and mean latency dropped 16.3 percent. And what we say honestly: planning factors are predictions, real numbers only appear after execution, and we keep the two separate on purpose."

(Demo cue: this is where you switch to the live app and show 6 ranked plans + the 51.1 percent deep-cut run.)

Slide 9 - Execution, the honest way

Say: "Execution has a fixed order enforced by the system: prune first, then export to ONNX, then quantize, and distillation last. Distillation is a real training run - a student network with half the width, six epochs, temperature two, KL loss scaled by temperature squared. And one rule I want to highlight: a run is never marked successful unless an artifact was actually written. The code literally refuses with the message 'refusing to mark run successful without proof'."

Slide 10 - Verification

Say: "After every run, both models get the same sixteen random inputs, fixed seed forty-two. Classifiers are compared by predicted class. We call it output agreement, never accuracy - it is a behavioural check, not a test-set result. The agreement percentage is stored with the run and shown in the interface. That is the proof layer of this project."

Slide 11 - What we ran it on

Say: "The platform has analyzed ResNet-18 - eleven point seven million parameters - plus smaller CNNs and MLPs. The results taught us one honest lesson: INT8 gives the best return for the least risk, distillation gives the best size reduction, and ONNX is not always faster on small models, because runtime overhead can beat graph fusion. We report the measured value instead of hiding it."

Slide 12 - AWS launch

Say: "One click in the interface launches an AWS GPU runner through boto3. The image is resolved live from SSM, the instance terminates on shutdown so it cannot keep billing. And your credentials stay yours - they are used for that one call, never written to the database. Wrong keys come back as a 401, missing permission as a 403, in plain language."

Slide 13 - Security and testing

Say: "Four layers. Traffic: rate limiting and security headers. Identity: signed tokens, twelve-hour lifetime, per-token revocation, passwords hashed with PBKDF2 at a hundred and twenty thousand rounds. Data: uploads and artifacts are encrypted at rest. Access: roles and ownership checked on every resource. And this is all proven by a test suite of a hundred and fifty-three checks in twenty-one sections against a live server - a hundred and fifty-three passed, zero failed."

Slide 14 - Live demo

Say: "Now the live part. Everything you saw on these slides is running right now."

The click path: "(1) Sign in with demo@modelsmith.io. (2) open MNIST Digit CNN in Projects. (3) show the analysis dashboard - parameter share, six ranked plans with reasons. (4) click Execute on the recommended plan - watch live progress. (5) show the result: size before and after, both artifacts, agreement percentage."

If they ask "is it really compressing?" - "Open the artifact list - the .pt and .onnx are there, with their file sizes measured after writing."

If they ask "what if a plan fails?" - "Show the job history - the failed job with its real error message, and the retry trail."

If the network plays up - "Reload the page once; the site finds a working backend among its tunnels. Worst case, I open the same app on this machine directly."

Slide 15 - Limits and next steps

Say: "What we state openly: single node, SQLite in WAL mode, agreement check instead of labelled accuracy, and guided-only TensorRT. Next: true accuracy measurement on labelled test sets, and real TensorRT builds on GPU runners."

Slide 16 - One sentence

Say: "The one sentence version: we measure the model instead of guessing, choose a compression plan that suits the device with clear written reasons, run it for real, and verify the smaller model still agrees with the original - with nothing counted as success until it is proven."
