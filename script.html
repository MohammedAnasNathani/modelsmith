ModelSmith Final Keynote Script

One full minute per slide, 16 slides, about 15 to 16 minutes total. Speak slowly. Wherever it says POINT, put your hand on that part of the slide. Lines in quotes are the words you can literally say.

SLIDE 1 - Title (1 min)

POINT at the logo and the four chip tags: PyTorch, ONNX Runtime, FastAPI, SQLite, AWS.

"Good morning everyone. Our final year project is ModelSmith. The tagline on top is the whole story in three lines: Analyze once. Optimize smart. Deploy anywhere.

We all know the uncomfortable truth about deep learning today. Training a model is now easy. Every student can train a ResNet in a notebook. But the model that works on the workstation almost never fits where it actually has to run. A phone has a few gigabytes of RAM. An edge device has even less. Nobody trains a model twice for every device by hand.

So we built one platform that solves this as a product, not as a script. You upload your trained model once. The platform measures it, decides how to make it smaller for the specific device you choose, actually performs the compression, and then proves to you that the smaller model still behaves like the original.

Everything on this deck is backed by a running system. At the bottom of this slide you can see the live demo link. It is hosted right now and we will show it working later."

SLIDE 2 - The problem (1 min)

POINT at the three numbered problems, then the two boxes at the bottom.

"Three concrete problems, and each one is what we designed against.

Problem one: we cannot see where the size is. Our ResNet-18 has eleven point seven million parameters, and most of them sit in a handful of layers. If you do not measure layer by layer, you are optimizing blind. You might spend days compressing a layer that holds two percent of the weights.

Problem two: choosing a method is guesswork. Quantize, prune, distill, export to ONNX. Each method costs some accuracy, each makes the file smaller, and combinations multiply the options. Today a person reads papers and guesses.

Problem three - and this is the dangerous one: nothing proves it still works. After compression, nothing in the usual workflow tells you whether the smaller model gives the same answers as the original. Broken models can ship quietly into production.

POINT at the diagram. The manual loop today: read the paper, guess a method, write an ad hoc script for one model, run it, hope the accuracy survives, and repeat for every model and every device.

That is the gap we built ModelSmith to close."

SLIDE 3 - The pipeline (1 min)

POINT at the five stage pills: Upload, Analyze, Plan, Execute, Download.

"The whole platform is five stages in one continuous flow.

Stage one, upload: you drop in a dot-p-t or ONNX file, and it is stored encrypted at rest. Stage two, analyze: we measure parameters, FLOPs, timing, and bottlenecks, layer by layer. Stage three, plan: the platform builds the best technique mix for your target device. Stage four, execute: it performs the real compression and benchmarks it. Stage five, download: you get the optimized model plus a full report.

Now the three lines on the right are what make this solid engineering and not a demo.

First, every stage writes its result to the database, so any run can be replayed later, and nothing depends on a browser tab staying open.

Second, jobs run in the background with live progress, so the page never freezes and you can literally close the tab and come back.

Third - the one we are proudest of: a failed job retries once, and if it fails again it reports the REAL error. It can never be marked successful by accident. If you see a green tick in ModelSmith, there is actually a file on disk behind it."

SLIDE 4 - Architecture (1 min)

POINT top to bottom: Browser, API, Worker, Database, and the AWS bubble.

"Here is how the pieces fit together, and I will keep it honest and simple.

The browser is plain HTML, CSS and JavaScript, hosted free - no framework lock-in. The API is FastAPI with more than sixty REST endpoints, and it checks the signed token on every single request. Inside the API process lives the job runner: two worker threads that retry once on failure. The worker is where PyTorch and ONNX Runtime do the real work - quantize, prune, export, distill, and benchmark on real tensors, not simulated numbers. The database is SQLite with eleven tables, write-ahead log mode, foreign keys switched on. And the optimized artifacts are stored encrypted on disk.

POINT at the AWS bubble on the right. On the far right: your machine or an AWS EC2 box can grab the model with a one-time token, compress it locally, and post the result back.

One deliberate choice on the bottom: no external queue. The runner lives inside the API process, so the whole project ships as one container. At this scale that is the right engineering call, and it keeps the system trivially deployable."

SLIDE 5 - Analyze (1 min)

POINT at the measure table, then the layer chart.

"Stage two: analysis. When a model lands, we measure it layer by layer before touching anything.

POINT row by row: Parameters - counted per layer, with their size in bytes. FLOPs - computed per layer type using forward hooks, so the count reflects the actual graph. Latency - five warm-up runs and then thirty timed runs, and we report the mean, not a lucky sample. We also record the ninety-fifth percentile, the slow tail, so bad cases are not hidden. Throughput - inferences per second from the same sample. And bottlenecks - the top three layers by parameter count with the share they hold.

Why this matters, in one line: it tells you which layer is actually expensive. Look at the chart on this slide - on our MNIST model, ONE layer holds seventy-three point five percent of all weights. If compressing anything, that is where the effort must go. Without this measurement you would be shaving the one point two percent layer.

So every later decision in the platform rests on real measured numbers from a real forward pass."

SLIDE 6 - Techniques (1 min)

POINT down the technique table column by column.

"Stage three starts with a knowledge base. Seven techniques we actually can run - not as names, as real code paths.

Look at the table. INT8 quantization: store weights with eight bits instead of thirty-two - about four times smaller, keeps about ninety-nine... sorry, ninety-eight point five percent accuracy. FP16: half precision, half the size with almost no quality loss. Pruning at twenty percent: remove the least useful filters so the model skips real work. Pruning at forty: same idea pushed harder, more risk. ONNX export: does not shrink the model but lets ONNX Runtime fuse operations, so it can make it faster. Distillation: train a small student network to copy the teacher - the most aggressive option. And a guided TensorRT path for GPU machines.

POINT at the two right columns. Each technique carries three numbers in the knowledge base: what it does to size, how much accuracy it typically keeps, and whether it can run on CPU. The planner multiplies these together to predict outcomes before running anything.

And to be fully honest with you: those accuracy numbers are PLANNING factors, not measurements. Measured numbers appear only after execution. We keep the two visibly separate everywhere."

SLIDE 7 - The algorithm (1 min)

POINT at the flow diagram top, formula center, example bottom.

"Now the heart of the project - how eight raw candidates become one recommendation.

Top flow: from seven techniques we generate eight candidate combinations. Then four gates. Does the hardware support it? No - rejected. Predicted accuracy above your floor? No - rejected. The rest get scored with the objective weights, sorted, and the best one is marked as recommended.

POINT at the formula. Read it out - it is the scoring formula: size saved times its weight, plus latency gain times its weight, plus memory saved plus accuracy kept with theirs. The weights come from the objective YOU pick. Balanced is zero point three, zero point three, zero point two, zero point two. Select smallest-size and size jumps to zero point five five, so the ranking reorders instantly.

Bottom line is the prediction model: size equals base size times the product of the technique factors; latency uses per-architecture factors, because a CNN and a tiny MLP respond to INT8 differently.

And the line I want the panel to remember: rejected plans are never thrown away. They stay visible with a written reason - for example, exceeds the accuracy floor, or requires a GPU for TensorRT. The planner always explains itself."

SLIDE 8 - The worked example (1.5 min)

POINT left card, then right card, then the green measured strip.

"Here is the planner doing real work on a real model.

Left card - edge-lite: INT8 quantization plus ONNX export. Predicted: seventy-five percent smaller, keeping about ninety-eight point five percent accuracy. Look at the note under it: the safe choice for a small device. This is the plan you take when you cannot spend accuracy.

Right card - edge-max: INT8 plus pruning at forty percent plus ONNX. Eighty-four point five percent smaller, keeping about ninety-two point six. The best size, but it eats into accuracy, and the card says exactly that in plain words.

Now the green strip in the middle is the part I can defend with an artifact: the measured result AFTER execution. On our demo CNN, the distillation plan took the file from ninety-three point eight kilobytes down to twenty-nine point seven - a measured sixty-eight point three percent smaller - and the same run measured sixteen point three percent faster, with output agreement verified. That is a real file that was written to disk, not a prediction.

Why the ranking is trustworthy - four lines: the estimate is transparent, you can see which multipliers produced it; anything the device cannot run is filtered BEFORE scoring; every plan, including rejected ones, carries written reasons; and after execution you can compare the predicted numbers against the real ones on the same screen.

We predicted, we ran, and we measure honestly. That is the whole method."

SLIDE 9 - Execute (1 min)

POINT at the four numbered steps and the code block.

"Stage four: execution. And the order of the steps is part of the method, enforced by the system, not left to the user.

Step one, prune - remove weights while the model is still dense. Step two, export to ONNX - capture the graph before precision is lowered. Step three, quantize INT8 or FP16 on the PyTorch copy. Step four, distillation - it is optional and it runs LAST, because it is a full retraining pass that produces the final file.

Why this order? POINT at the note. Structured pruning needs to identify whole filters from weight magnitudes. Once the weights are quantized, that identification is no longer reliable. So pruning must happen first - and the code enforces it rather than trusting the user.

POINT at the code for the engineers in the room. Quantization uses torch.quantization.quantize_dynamic on linear, LSTM, GRU and RNN layers, per-channel INT8. Pruning uses structured L2 pruning along output channels for convolutions and L1 unstructured for linear layers - and then prune dot remove makes the masks permanent, so the deleted filters are really gone from the file, not zeroed on paper."

SLIDE 10 - Verify (1 min)

POINT at the diagram: original model and optimized model running side by side.

"Stage five: verify. This is the layer that turns this from a tool into something you can trust.

The idea is simple enough to say in one sentence: run BOTH models - the original and the compressed one - on the same sixteen random inputs, generated with fixed seed forty-two, and compare the outputs per input. Fixed seed means anyone can repeat it on any machine and get the same verdict.

POINT at the two kinds of check. For classifiers, we compare the predicted class - argmax of both outputs. For other outputs, we compare numerically with a tolerance of zero point zero five, using allclose. The agreement percentage is then saved with the run and shown in the interface.

And now the honest part - POINT at it. We call this output agreement, and we never call it accuracy. It is a behavioural check: does the smaller model answer the same way as the bigger one. It is not a test-set score. We label it that way everywhere in the product, and in our demo runs it came out at one hundred percent agreement.

Small model, same behaviour, proven input by input. That is our definition of success."

SLIDE 11 - Results (1 min)

POINT at the three big numbers, then the model table.

"Real numbers from the running system, all measured by the platform itself.

Sixty-eight point three percent smaller - the distillation run on our demo CNN: the artifact on disk went from ninety-three point eight KB to twenty-nine point seven KB. Sixteen point three percent faster - same run, same machine, mean latency from zero point one two nine milliseconds to zero point one zero eight. Fifty-one point one percent smaller - the deep-cut plan, INT8 with pruning and ONNX, which produced BOTH artifacts, a dot-p-t and a dot-o-n-n-x.

POINT at the table. The platform has analyzed three models so far. MNIST CNN: twenty-one thousand eight hundred forty parameters, zero point three three milliseconds latency, ninety-three point eight KB on disk. CIFAR-10 CNN: five hundred sixty-eight thousand parameters, zero point six three milliseconds, two point three MB. ResNet-18: eleven point seven million parameters, four point four six milliseconds, forty-six point eight MB.

What the results taught us - the honest lesson at the bottom: size reduction is the RELIABLE win, it follows directly from precision and pruning ratios. Latency and speed depend on the hardware and the runtime - on some setups ONNX is actually slower, because for tiny models the runtime overhead beats graph fusion. We report the measured value instead of hiding it."

SLIDE 12 - Run anywhere (1 min)

POINT at Option A and Option B cards.

"The same plan can run in two places, and the user chooses.

Option A: on the platform. The job runs in our worker threads - zero setup, fastest to start, it shares our CPU.

Option B: on your infrastructure. The platform mints a one-time token. Your machine downloads the model and the plan with that token, compresses it locally, and posts the artifacts back. Your data and your GPU never leave your side. That is the right pattern for people with private data.

POINT at the AWS block. And we made the AWS launch built in. The interface starts an EC2 instance through boto3, resolves the current Amazon Linux 2023 image live from SSM so it never goes stale, gives it a thirty GB disk, and sets it to terminate on shutdown - so it physically cannot keep billing you after the job.

POINT at the keys line. The credentials stay yours: the keys are used for that single API call and are never written into the database. Wrong keys come back as a clean 401, missing permission as a 403, in plain language. Security by default, not as an afterthought."

Now the bar at the bottom is the proof this all actually works - POINT at it. A test suite of one hundred fifty-three end-to-end checks running against a LIVE server, in twenty-one sections. SLIDE 15 - Limits and next steps (1 min)

POINT at the limits list first - say this one confidently, it earns respect.

"We state our limits openly, because pretending is exactly the kind of failure this project exists to remove.

Latency is measured on the machine that runs the job - CPU only in this deployment. Accuracy retention during planning is an estimate from published factors, not a measurement from a labelled test set. FP16 and TensorRT only pay off fully on GPU runtimes. And storage is a single SQLite file - the right tool at this scale, not a cluster.

POINT at next steps. What we would do next, in priority order: dataset-backed accuracy testing before and after each plan - that is first, it closes the last honesty gap. Real TensorRT builds on GPU runners with on-device timing. A calibration loop: feed measured results back to correct the planner's factors, so predictions keep improving. Batch mode across many models with a cost estimate per plan. And running the optimized model directly in the browser to show it live."

SLIDE 16 - Glossary and closer (1 min)

POINT at the terms table - walk it fast and friendly.

"Before closing, one slide of plain language. These are the words we used today, defined the way a non-expert would want.

A parameter is one learned number inside the model - more parameters usually means a bigger file. FLOPs is a rough count of the arithmetic needed for one prediction. Quantization means storing those numbers with fewer bits - eight instead of thirty-two makes the file roughly four times smaller. Pruning means deleting the least useful weights so the model does less work. Distillation means training a small model to imitate a large one. ONNX is a common file format, so different runtimes can load the same graph. And TensorRT is NVIDIA's GPU runtime, which builds an engine specialized for one GPU.
