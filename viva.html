Page 1: The 60 second pitch

What it is. A web platform where you upload a trained neural network, and it measures the model, suggests how to make it smaller for a chosen device, runs that plan for real, and proves the smaller model still gives the same answers.

Why it exists. Making a model smaller is normally expert work done by hand. You guess which of several methods to combine, you write an ad hoc script, and nothing tells you whether the compressed model still behaves correctly. ModelSmith turns that into one pipeline with recorded reasons and measured proof.

The five stages. Upload (encrypted at rest), Analyze (parameters, FLOPs, timing, bottlenecks), Plan (ranked options for a target device), Execute (real compression and benchmarking), Download (optimized model plus a report).

One sentence if you are put on the spot. "We measure the model properly, choose a compression plan that suits the device with clear reasons, run it for real, and verify the smaller model still agrees with the original."

Page 2: The algorithm, explained simply

Planning

We keep a knowledge base of seven techniques: INT8 quantization, FP16, pruning at 20 percent, pruning at 40 percent, ONNX export, distillation, and a guided TensorRT path. Each one carries declared multipliers: how much smaller it usually makes a model, how much faster, and how much accuracy it typically keeps.

From that base we build eight candidate combinations, for example edge-lite is INT8 plus ONNX, and edge-max is INT8 plus pruning at 40 percent plus ONNX.

Every candidate then goes through four steps:

  1. Predict. Multiply the technique factors together to get expected size, latency, memory and accuracy.

Latency factors are looked up per architecture class, because a CNN and a small MLP do not respond to INT8 in the same way.

  1. Filter. Drop anything the target hardware cannot run, and drop anything below your minimum accuracy floor.
  2. Score. score = w_size * size_saved + w_latency * latency_gain + w_memory * memory_saved + w_accuracy * accuracy_kept.

The weights come from the objective you pick. Balanced is 0.30, 0.30, 0.20, 0.20. Choosing "smallest size" sets size to 0.55.

  1. Rank. Sort by score, mark the top plan as recommended, and keep the rejected ones with the written reason.

Why this is defensible: the planner never decides anything by magic. It predicts with visible factors, filters with explicit rules, and scores with published weights. Rejected plans are shown with reasons such as "exceeds the accuracy floor" or "requires a GPU for TensorRT".

Execution

The order of operations is part of the method, and it is: prune, then export to ONNX, then INT8 or FP16, and distillation last.

  • INT8 quantization uses torch.quantization.quantize_dynamic on the linear, LSTM, GRU and RNN layers with per channel

scales. Dense layers get roughly four times smaller.

  • Pruning uses structured L2 pruning along the output channels for convolutions, which removes whole filters, and

unstructured L1 pruning for linear layers. Then prune.remove makes the masks permanent. Achieved sparsity is measured, not assumed.

  • ONNX export uses opset 13 and is validated with onnx.checker.check_model before anyone calls it a success.
  • Distillation is a real training run: a student with half the width, six epochs, 512 samples, batch 32, temperature 2,

Adam at 1e-3, and KL divergence scaled by temperature squared. The per epoch loss history is stored with the run.

  • TensorRT is guided only. We do not pretend to build a GPU engine on a CPU machine.

One rule you should memorise: a run is never marked successful unless an artifact was actually produced. The code refuses with the message "refusing to mark run successful without proof".

Verification

Both models get the same 16 random inputs, generated with a fixed seed of 42. Classifiers are compared by predicted class, other outputs by a small numeric tolerance. The agreement percentage is stored with the run and shown in the interface. We call it output agreement, never "accuracy", because it is a behavioural check and not a test set result.

Page 3: Expected questions, with answers

Q: What exactly is new in this project? Three things: the planner that predicts, filters and ranks plans against a target device with written reasons; an executor that really performs quantization, pruning, ONNX export and distillation rather than simulating them; and a verification step that refuses to report success without an artifact and an agreement check.

Q: How do you prove the compression is real? The artifact file size is measured after writing, and latency is measured by running both models 30 times after 5 warm up passes. On our distillation run the artifact went from 93.8 KB to 29.7 KB, which is a 68.3 percent reduction, and mean latency dropped from 0.129 ms to 0.108 ms.

Q: Is the accuracy number in the planner real? No, and we say so. Those are published planning factors used to filter and rank candidates. Measured numbers only appear after execution. We keep the two visually and verbally separate on purpose.

Q: Why is ONNX sometimes slower on your CPU? Because for very small models the runtime overhead can be larger than the gains from graph fusion. We report the measured value instead of hiding it. The reliable win from compression is file size, and latency gains depend on the runtime and the hardware.

Q: Why did you not measure true accuracy? That needs a labelled test set, which our demo models do not ship with. It is the first item on our roadmap, together with real TensorRT builds on GPU runners.

Q: How many techniques, and which one is best? Seven, and there is no single best one. It depends on the target device and how much accuracy you can spend. Distillation usually gives the best size reduction, INT8 gives the best return for the least risk, and TensorRT gives the best GPU latency.

Q: What happens if a job crashes? Jobs are rows in the database with statuses. A crashed job is re-queued on the next start, a failed job retries once and then fails permanently with the real error. A run is never left in a lying state.

Q: Why is pruning done before quantization? Because structured pruning needs to identify whole filters from the weight magnitudes. After quantization the weights are stored differently, so that identification is no longer reliable. The executor enforces the order rather than trusting the user.

Q: How does the system scale? Honestly: it is a single node design. The job runner is a thread pool inside the API process, which is right for this scale. Scaling up would mean moving the queue to a broker and running workers separately, which the current job table already supports in shape.

Page 4: Cloud, security and engineering

Q: How does the AWS part work? From the interface we call ec2.run_instances through boto3. The Amazon Linux 2023 image is resolved live from SSM, the instance gets a 30 GB gp3 disk, and it is set to terminate on shutdown so it cannot keep billing. The startup script installs Python, PyTorch and ONNX Runtime, downloads the runner, and shuts the machine down when it finishes.

Q: Where do the AWS keys go? Nowhere. They are used for that single call and never written to the database. Wrong keys come back as a clear 401, missing permission as a 403, and network problems as a 502 with the AWS message.

Q: What is the runner protocol? A run can be marked "waiting for runner". The platform mints a single use token with a 24 hour lifetime. The runner downloads the manifest and the decrypted model, compresses it locally, reports progress, and posts the artifacts back as base64. Empty artifacts are rejected, and the token is burned when the run finishes.

Q: How do you handle security? Four layers. Traffic: request rate limiting, stricter limits on failed logins, security headers, request IDs. Identity: signed tokens with a 12 hour lifetime, per token revocation and a sign out everywhere option, passwords hashed with 120,000 rounds of PBKDF2 with a per user salt. Data: uploads and artifacts are encrypted at rest, SQLite runs in write-ahead log mode with foreign keys on, and there is a one click database backup. Access: member and admin roles, ownership checked on every resource, and an audit log of actions.

Q: How did you test it? With a suite of 153 checks that runs against a live server, in 21 sections. It boots the app, registers users, uploads a model, waits for real jobs, and inspects real artifacts. It also covers the whole runner protocol, AWS error handling, cross user access attempts, oversized input, forged tokens, the rate limiter, and the security headers. Result: 153 passed, 0 failed.

Q: Why SQLite and not Postgres? For a single node project that has to be trivially runnable and backup-able, SQLite in WAL mode is the right tool. It supports concurrent reads during writes, it has real transactions, and the whole database is one file. Moving to Postgres later is a contained change because all the access is behind one module.

If you do not know something

Say this: "We did not measure that, and I would not want to guess. What I can tell you is what we did measure, which is this." Then give a real number. Admissions like that are respected more than invented figures, and the project already follows that rule everywhere.

If a live demo fails in front of them

Reload the page once. The site looks for a working backend among three tunnels, so a reload usually fixes it. If it does not, open http://127.0.0.1:8100 on the laptop, which is the same application with the same data. Say plainly: "the deployment runs on this machine today, and the production path is the AWS launch you can see in the interface."

The three sentences that carry the whole project

  1. "We measure the model instead of guessing, so every number in the report comes from a real forward pass."
  2. "The planner predicts, filters and ranks plans, and it always explains why something was rejected."
  3. "Nothing counts as a success unless an artifact was produced and the compressed model still agrees with the original."
