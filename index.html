01 · The problem

Training a model is easy.
Making it fit is the hard part.

02 / 16

1. We cannot see where the size is

Our ResNet-18 has 11.7 million parameters and most of them sit in a few layers. Without measuring, we are optimizing blind.

2. Choosing a method is guesswork

Quantize, prune, distill, export to ONNX. Each one costs some accuracy, and combinations multiply the options.

3. Nothing proves it still works

After compression nothing tells us whether the smaller model gives the same answers. Broken models can ship quietly.

The manual loop today

  • Read the paper, guess a method
  • Write an ad hoc script for one model
  • Run it, hope accuracy survives
  • Repeat for every model and every device

Days of work, no record of what was tried.

What we built instead

  • One pipeline: upload, analyze, plan, execute, download
  • Plans are ranked and explained, rejected ones say why
  • Every number is measured on the machine that ran it
  • The output is verified against the original before it counts

What we collect

MeasureHow we get it
Parameterscounted per layer, and their size in bytes
FLOPscomputed per layer type with forward hooks
Latency5 warm up runs, then 30 timed runs, reported as the mean
p95 latencythe slow tail, so we do not hide bad cases
Throughputinferences per second from the same sample
Bottleneckstop three layers by parameters, with the share they hold

Why this matters

It tells us which layer is actually expensive. On our MNIST model one layer holds most of the weights, so that is where any compression effort has to go.

Example: parameter share by layer

Benchmark rule

Timings always come from real forward passes on the machine that ran the job, never from a datasheet. If a runtime cannot do something (for example FP16 on a plain CPU) we say so instead of inventing a number.

Hardware profiles

Five targets: CPU server, GPU server, edge device, mobile, and web browser. Each one declares its memory budget and which precisions and runtimes it can actually run.

Why profiles matter

TensorRT is rejected unless the target is a GPU server. INT8 is rejected on a profile that cannot do integer math. The planner never recommends something the device cannot run.

Read this table carefully

The size and accuracy columns are planning estimates, not measured results. Real numbers appear after execution, and we keep the two clearly separate.

MODELSMITH05 · PLAN
06 · The algorithm

From eight candidates to one recommendation

07 / 16

The scoring formula

score = w_size * size_saved
      + w_latency * latency_gain
      + w_memory * memory_saved
      + w_accuracy * accuracy_kept

The weights come from the objective you choose. Balanced uses 0.30, 0.30, 0.20, 0.20. Ask for "smallest size" and size gets 0.55, so the ranking changes instantly.

Predicting before running

size    = base_size    * product(size_factor)
latency = base_latency * product(latency_factor[arch])
memory  = base_size    * product(mem_factor) * 1.2
accuracy= product(accuracy_factor)

Latency factors depend on the architecture, because a CNN and a small MLP do not respond to INT8 in the same way. The 1.2 on memory accounts for runtime overhead.

Why the ranking is trustworthy

  • The estimate is transparent: you can see which multipliers produced it
  • Anything the device cannot run is filtered out before scoring
  • Every plan carries written reasons, including the rejected ones
  • After execution the predicted and real numbers sit next to each other

What we say honestly

Planning uses declared factors, so a plan is a prediction. Only execution produces measured results. That separation is deliberate: it stops us from presenting a guess as a fact, and it gives us a calibration loop for the next version.

MODELSMITH07 · WORKED EXAMPLE
08 · Stage 4, execute

The order of the steps is part of the method

09 / 16

What each step really does

# quantization: per channel INT8
torch.quantization.quantize_dynamic(
  model, {Linear, LSTM, GRU, RNN}, dtype=torch.qint8)

# pruning: real filter removal, made permanent
ln_structured(conv, amount, n=2, dim=0)
l1_unstructured(linear, amount)
prune.remove(module, "weight")

# export, validated before it is accepted
torch.onnx.export(model, dummy, opset_version=13)
onnx.checker.check_model(graph)

Distillation is a real training run

# student is half the width of the teacher
student = build_student(teacher)
# 6 epochs, 512 samples, batch 32, temperature 2
loss = KLDiv(log_softmax(s/T), log_softmax(t/T)) * T*T
Adam(lr=1e-3)  -> per epoch loss is recorded
  • The smaller student is genuinely cheaper, not just stored differently
  • Loss history is returned with the run so you can see it converge
  • If a student cannot be built, we fall back instead of failing
  • No artifacts, no success: a run without output is refused
MODELSMITH08 · EXECUTE
09 · Stage 5, verify

Smaller is only useful if it still agrees

10 / 16

Same inputs, same seed

Both models get identical random inputs generated with a fixed seed, so the comparison is repeatable on any machine.

Two kinds of check

Classifiers are compared by their predicted class. Other outputs are compared with a small numeric tolerance.

The honest part

Agreement is a behavioural check, not a test set accuracy. We label it that way everywhere in the interface instead of pretending it is a benchmark score.

What the results taught us

  • Size reduction is the reliable win. It follows directly from precision and pruning ratios.
  • Latency depends on the hardware. On a tiny CPU model, ONNX Runtime overhead can outweigh graph fusion, and we report that instead of hiding it.
  • Distillation gave the best trade off here, because the student is genuinely smaller.
  • Predicted versus measured can be compared after every run, which is the calibration loop we want next.

AWS launch, built in

The interface starts an EC2 instance with boto3, takes the current Amazon Linux 2023 image from SSM, gives it a 30 GB disk, and sets it to terminate on shutdown so it cannot bill forever.

Credentials stay yours

Keys are used for that single call and are never written to the database. Missing permission and bad keys come back as clear errors, not vague failures.

Why this matters in practice

Companies rarely want to upload model weights to someone else's server. This design lets them keep the compute and the data, while still using our planner and our verification.

15 · Plain language reference

The words, explained simply

16 / 16
TermWhat it means here
Parameterone learned number inside the model. More parameters usually means a bigger file.
FLOPsfloating point operations, a rough count of the arithmetic needed for one prediction.
Quantizationstoring the numbers with fewer bits. 8 bits instead of 32 makes the file about four times smaller.
Pruningdeleting the least useful weights or filters so the model does less work.
Distillationtraining a small model to imitate a large one.
TermWhat it means here
ONNXa common file format for models, so different runtimes can load the same graph.
TensorRTNVIDIA's GPU runtime. It builds an engine that is specific to one graphics card.
Structured pruningremoving whole filters, which saves real time, not just space.
Output agreementhow often the compressed model gives the same answer as the original on the same inputs.
Artifactthe file we produce at the end, either a .pt or an .onnx model.

The one sentence version

We measure a model properly, choose a compression plan that suits the device with clear reasons, run it for real, and check that the smaller model still behaves like the original.
